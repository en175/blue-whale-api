# 对客档位契约不同则新开渠道类型，即使上游与豆包直连相同

抽签降档与真 1080 直连共用火山 Seedance 的协议、端点与鉴权，但按请求档对客计费、对上可抽签。词表原定义「渠道边界 = 上游协议/端点/鉴权」无法表达这条差异，故新开渠道类型，并把渠道边界扩到对客档位契约。

**Status:** accepted

## 背景

ADR 0003 规定：参数一致但上游不同，必须是不同渠道（XFAI vs 豆包）。本次「抽签渠道」的上游与豆包直连可以完全相同，差别只在对客档位契约。若复用 DoubaoVideo、只在 `setting` 里开关，运营无法用 priority/weight 把「真 1080」和「抽签」拆成两条独立路由，对账也要翻 JSON。

## 决策

新开独立 task 渠道类型（嵌入豆包 adaptor，不复制协议实现）。协议/端点/鉴权委托豆包；分辨率抽签、按请求档重算视频 token、对客响应改写由新类型承担。

## 理由

运营需要把两种对客契约当成可独立加权的渠道。上游相同不是复用类型的理由。

## 后果

- 同一把上游 Key 可以挂两条渠道：一条 DoubaoVideo，一条抽签类型。
- 读者若只看 ADR 0003，会误以为「上游相同就必须同一类型」；以本 ADR 为准。
