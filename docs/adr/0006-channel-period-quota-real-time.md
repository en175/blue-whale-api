# 渠道周期限额判定改为 Redis 近实时（Tier 1），硬上限维持内存缓存判定

IK9W58 双限额上线后，周期限额与硬上限都靠 SYNC_FREQUENCY（60s）一次的内存渠道快照判定，Redis 周期计数（`IncrChannelPeriodQuota`）只写不读。本次把**周期限额**判定改为判定时读 Redis 计数器（近实时），**硬上限**维持 60s 内存判定；Redis 未启用 / 读失败 / key 不存在时回退内存快照叠加未批量落库增量。

**Status:** accepted

## 背景

`DeductChannelQuota` 每笔扣费同步 INCR Redis 周期计数并（按配置批量）落库，`ChannelIsQuotaExceeded` 却只读内存渠道快照——最快 60s 才刷新一次，超限渠道在窗口期内仍会被选中，Redis 计数成了无人消费的写侧。本次把它接入判定。

## 决策

1. **Tier 1（近实时读）**：判定时对每个候选渠道读一次 Redis 周期计数，作为周期已用额度；不做 Tier 2 原子预订。
2. **只实时化周期限额**：硬上限维持 60s 内存判定（终身累计，无周期滚动窗口，不值得多一次 Redis 读）。
3. **降级方向**：Redis 未启用 / 读失败 / key 不存在 → 回退内存 `PeriodUsedQuota` 叠加 `pendingBatchDelta`（未批量落库增量）。不 fail-open 到 0（防 Redis 重启丢 key 误放行），不 fail-closed 拒绝（防 Redis 抖动误杀流量）。实现上**仅当 Redis 值 > 0 且 ≥ 内存快照 + 未落库增量时才采用**（正常态恒成立）：既用「> 0」判定 key 存在，又防某次 INCR 写失败或重启重建把计数留在低位、被误采用导致漏拦超限渠道。
4. **异步任务计费语义不动**：任务提交时预记估计额度、退款不扣回渠道计数。计数偏大只会让受限渠道更早分流兜底，不会超限（方向安全）。
5. **性能**：每个候选渠道单独 GET 一次，不批量 MGET、不做本地短缓存（候选集通常 1~5，Redis 内网读亚毫秒级）。

## 被否掉的选项

- **Tier 2（Lua 原子预订，真硬限）**：需把选渠道改为预订语义并处理跨进程回滚，复杂度高；Tier 1 已满足「超限后亚秒级分流兜底」的目标。
- **硬上限也实时**：终身累计不存在周期滚动窗口，60s 滞后的影响仅是「到限后最多晚 60s 停用」，不追加 Redis 读。
- **Redis 失败 fail-open（视为 0）**：Redis 重启丢 key 会放行超限渠道，违反方向安全。
- **Redis 失败 fail-closed（拒绝）**：Redis 抖动会误杀全部流量，兜底渠道形同虚设。
- **异步任务退款扣回渠道计数**：要新开递减路径，且跨周期失败（提交在周期1、失败在周期2）会扣错周期的 key，风险大于收益。

## 后果

- **残留竞态**：判定（读）与扣减（写）之间仍有 check-then-act 窗口，并发在途请求可能越过限额，由兜底渠道吸收。
- **Redis 重启丢 key / 计数失步**：空 key 或 Redis 值低于内存估计（INCR 写失败、key 重建）时回退内存最近同步值（保守），不误放行。
- **计数偏大**：异步任务预记不回收，受限渠道可能比真实消耗更早达限，流量提前分流兜底。
- **Redis 计数与内存快照以 max 语义收敛**：判定仅当 `Redis ≥ 内存快照 + 未落库增量` 时采用 Redis（正常态恒成立），否则取内存估计——既不放弃实时性，也不让失步低位漏拦。读路径限时 200ms，Redis 卡顿快速失败回退，避免选渠道热路径被冻结。
- **代码落点**：`service/channel_quota_redis.go` 整体迁到 `model/channel_quota_redis.go`（model 不能 import service，读侧需在 model 包内），service 两处调用点改 `model.` 前缀；判定函数新增 Redis 优先逻辑，配套 miniredis 回归测试。
