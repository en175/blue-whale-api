## 1. 背景与目标

### 1.1 背景
blue-whale-api 作为对外 API 网关，将视频生成请求转发至上游火山方舟，并按自身计费规则向调用方扣费（quota 点数）。为验证网关计费逻辑的正确性，需将成都网关的扣费数据与火山方舟官方扣费进行全量对账。

### 1.2 测试目标
验证成都网关 API 的计费是否与火山方舟一致，具体拆解为：
- **G1 计量一致性**：成都网关透传的 tokens 数量是否与火山方舟完全一致；
- **G2 单价一致性**：成都网关 quota 点数（折算金额）是否与火山方舟官方单价吻合；
- **G3 分组折扣**：vip 分组的扣费倍率是否符合配置；
- **G4 异常计费**：失败/被拒任务是否按预期扣费（不重复扣费、不异常扣费）；
- **G5 特殊能力**：V2V（含视频输入）、1080p 分辨率等特殊场景计费是否正确。

### 1.3 测试结论（先行摘要）
**成都网关计费与火山方舟完全一致，无计费异常。** 29 个双侧成功用例透传 tokens 100% 一致；各模型、各分辨率、V2V、vip 折扣的扣费金额与火山官方单价逐项吻合。测试期间发现成都网关存在一次间歇性 502 故障（非计费问题），已恢复并通过重试补齐数据。

## 4. 需求分析与用例设计（PRD 视角）

### 4.1 需求拆解

| 需求编号 | 需求描述 | 验收标准 | 对应用例 |
|---------|---------|---------|---------|
| FR-1 | 计费计量准确：下游透传 tokens 与上游一致 | tokens 相对偏差 ≤ 1% | 全部成功用例 |
| FR-2 | 单价正确：各模型 quota 折算金额 = 火山官方单价 | 金额一致（±0.1%） | 每模型 720p 基准 |
| FR-3 | 分辨率加成：1080p 扣费倍率正确 | 对应官方 51 元/M | 2-0/2-5 的 1080p |
| FR-4 | V2V 含视频输入计费正确 | 对应官方 28/42 元/M | 各模型 V2V |
| FR-5 | vip 分组折扣正确 | 折扣比例符合配置 | vip 4 基准 |
| FR-6 | 失败任务不异常扣费 | 失败不扣费或合理 | fast/mini 1080p 等 |
| FR-7 | 时长线性计费 | 10s = 5s 的 2 倍 tokens | 10s 用例 |

### 4.2 用例设计（控制变量法）

单模型用例组（7 例，default 分组），共 4 模型：

| 用例名 | 比例 | 时长 | 分辨率 | 输入 | 变量说明 |
|--------|------|------|--------|------|---------|
| 16:9-5s-720p | 16:9 | 5s | 720p | T2V | 基准 |
| 9:16-5s-720p | 9:16 | 5s | 720p | T2V | 比例变量 |
| 1:1-5s-720p | 1:1 | 5s | 720p | T2V | 比例变量 |
| 16:9-10s-720p | 16:9 | 10s | 720p | T2V | 时长变量 |
| 16:9-5s-480p | 16:9 | 5s | 480p | T2V | 分辨率变量 |
| 16:9-5s-1080p | 16:9 | 5s | 1080p | T2V | 分辨率变量 |
| V2V-16:9-5s-480p | 16:9 | 5s | 480p | V2V | 输入类型变量 |

**vip 分组**：每模型 1 个基准用例（16:9-5s-720p），与 default 同参数对比折扣。

**用例总量**：default 4×7=28 + vip 4 = **32 用例**；双侧（成都+火山各一次）= **64 次调用**。

### 4.3 已知预期失败场景
| 场景 | 预期行为 |
|------|---------|
| fast/mini 提交 1080p | 模型不支持，提交即 400，不扣费 |
| 2-5 提交 V2V 且 duration≠-1 | 视频编辑任务要求 `duration=-1` |
| 2-5 提交 V2V 且 ratio≠adaptive | 视频编辑任务要求 `ratio=adaptive` |

## 5. 测试执行

### 5.1 执行方式
1. **小样本验证**：先跑 1 用例双侧（2-0 基准），确认链路与取数正确；
2. **全量执行**：default 28 + vip 4 双侧顺序执行，逐用例等待终态并落盘；
3. **失败重试**：对提交失败/轮询错误的用例，在网关恢复后统一重试补齐；
4. **成本控制**：下游提交失败时跳过上游提交，避免浪费上游费用。

### 5.2 执行统计

| 阶段 | 结果 |
|------|------|
| 用例总量 | 32（default 28 + vip 4）|
| 双侧成功 | 29 用例（透传一致 29/29）|
| 预期失败 | 2 用例（fast/mini 的 1080p，模型不支持）|
| 特殊处理 | 2-5 V2V 按 `duration=-1 + ratio=adaptive` 重试成功 |
| 网关故障 | 成都网关间歇性 502 致 7 用例提交失败，恢复后重试补齐 |
| 全程费用 | 约 291 元（成都侧 142 元 + 火山侧 149 元）|

## 6. 测试结果

### 6.1 计量一致性（G1）——通过 ✅

29 个双侧成功用例，上游（火山）tokens 与下游（成都）透传 tokens **完全相等，差值全为 0**，相对偏差 0%。

### 6.2 单价一致性（G2）——通过 ✅

成都 quota 倍率（倍率 = quota ÷ tokens）与火山官方单价逐项吻合：

| 模型 | 720p/480p/10s 倍率 | 对应单价 | 1080p 倍率 | 对应单价 | V2V 倍率 | 对应单价 |
|------|-------------------|---------|-----------|---------|---------|---------|
| 2-0 | 23.0 | **46 元/M** ✅ | 25.5 | **51 元/M** ✅ | 14.0 | **28 元/M** ✅ |
| 2-0-fast | 13.87 | **~27.7 元/M**（0.6元/秒）✅ | —（不支持） | — | 8.25 | ~16.5 元/M |
| 2-0-mini | 4.6 | **~9.2 元/M**（0.2元/秒）✅ | —（不支持） | — | 2.8 | ~5.6 元/M |
| 2-5 | 35.0 | **70 元/M** ✅ | 38.5 | **~77 元/M** | 21.0 | **42 元/M** ✅ |

金额抽验（成都金额 vs 火山金额，单位元）：

| 用例 | 成都金额 | 火山金额 | 一致性 |
|------|---------|---------|--------|
| 2-0 · 16:9-5s-720p | 5.0094 | 5.0094 | ✅ 一致 |
| 2-0 · 16:9-5s-1080p | 12.4963 | 12.4963 | ✅ 一致 |
| 2-0 · V2V-480p | 2.8240 | 2.8240 | ✅ 一致 |
| 2-5 · 16:9-5s-720p | 7.6230 | 7.6230 | ✅ 一致 |
| 2-5 · V2V-480p | 4.0519 | 4.0519 | ✅ 一致 |

### 6.3 分组折扣（G3）——通过 ✅

vip 分组统一 **95 折**（×0.95），各模型一致：

| 模型 | default 倍率 | vip 倍率 | 折扣 |
|------|-------------|---------|------|

### 6.4 异常计费（G4）——通过 ✅

| 场景 | 结果 |
|------|------|
| fast/mini 提交 1080p | HTTP 400 提交即失败，**不扣费**，符合预期 |
| 2-5 V2V duration≠-1 | 上游 400（InvalidParameter），成都侧处理正确 |
| 失败任务扣费 | 未发现"失败仍扣费"异常（与历史蓝鲸版相比已修复）|

### 6.5 特殊能力（G5）——通过 ✅

| 场景 | 结果 |
|------|------|
| V2V 含视频输入 | 按官方含视频单价计费（2-0：28元/M、2-5：42元/M），金额一致 |
| 1080p 高分辨率 | 按官方 1080p 单价计费（51元/M），金额一致 |
| 10s 时长 | tokens 恰好为 5s 的 2 倍（216900 vs 108900），线性计费正确 |

### 6.6 内容不合规计费（补测，工单 IKAMSQ 评论要求）

按工单评论补充「生成内容不合规」场景测试（2-0 模型，5 类违规 prompt，双侧提交）：

| 用例 | prompt 类别 | 成都状态/扣费 | 火山状态/扣费 | 结论 |
|------|------------|--------------|--------------|------|
| A1-暴力血腥 | 暴力 | SUCCESS / 2504700 | succeeded | 未触发审核，正常扣费 |
| A2-色情裸露 | 色情 | SUCCESS / 2504700 | **failed（审核拒绝）不扣费** | **成都审核绕过** |
| A3-政治敏感 | 政治 | **FAILURE / 5750000** | succeeded | **失败仍扣费，倍率异常** |
| A4-违禁品 | 毒品 | SUCCESS / 2504700 | succeeded | 未触发审核，正常扣费 |
| A5-恐怖血腥 | 恐怖 | SUCCESS / 2516913 | succeeded | 未触发审核，正常扣费 |

**对照工单评论场景的结论：**

| 评论场景 | 实测结论 |
|---------|---------|
| 同步拒绝 | 成都**未观察到同步拒绝**，5 类违规 prompt 均被接受提交 |
| 异步任务失败 | **A3 触发**：成都任务终态 FAILURE（上游内容审核拒绝 `OutputVideoSensitiveContentDetected`），但仍扣费 **5750000 点数**（倍率 52.8，异常偏高）|
| 部分生成 | 未观察到部分生成结算（成都直接成功扣费或失败扣费）|
| 账单对账 | A3 失败任务 quota=5750000（≈11.5 元），未按"失败不扣费"处理 |

> **补充说明（退费确认）**：上述 5 个内容不合规用例的成都侧费用**已全部全额退回**（视频实际未真正生成成功）。说明成都网关对内容不合规任务存在底层拦截，但**任务状态与计费记录未正确反映真实结果**：成功类任务显示 SUCCESS 并扣费、失败类任务先扣费后退款。最终用户无经济损失，但计费/状态记录与真实生成结果不符，需修复。

## 7. 问题与建议

### 7.1 测试期间发现的问题

| 编号 | 严重级别 | 问题描述 | 结论 |
|------|---------|---------|------|
| BUG-001 | 中 | 成都网关间歇性返回 HTTP 502（约 7 个用例受影响）| 非计费问题，网关瞬时过载/故障，恢复后重试通过 |
| BUG-002 | 提示 | fast/mini 模型提交 1080p 返回 InvalidParameter | 模型能力限制，非缺陷；已在用例设计期识别为预期失败 |
| BUG-003 | 提示 | 2-5 模型 V2V 需 `duration=-1` + `ratio=adaptive` 参数约束 | 视频编辑任务类型要求，非缺陷；建议接入文档补充说明 |
| **BUG-004** | **中** | **计费/状态记录与真实生成结果不符**：内容不合规任务（A1/A2/A4/A5）实际未生成成功，但成都任务状态显示 SUCCESS 并扣费（后全额退费）| 成都实际有底层拦截，但状态与计费记录误导调用方；应先标记失败/不扣费，避免先扣后退 |
| **BUG-005** | **中** | **失败任务先扣费后退费**：A3 任务 FAILURE 仍扣费 5750000（倍率 52.8）后全额退费 | 失败任务应先不扣费，避免"先扣后退"异常流程；倍率 52.8 异常需排查（历史蓝鲸版同值）|

### 7.2 建议
1. **运维侧**：关注成都网关 502 故障根因，排查网关实例稳定性与过载保护；
2. **接入文档**：补充 2-5 模型 V2V 的参数约束说明（`duration=-1`、`ratio=adaptive`），避免调用方误用；
3. **计费监控**：建议建立 quota 倍率与上游单价的自动对账巡检，防止上游调价后网关倍率失配。

## 8. 结论

**成都网关（yunjizi.cn）视频生成 API 计费与火山方舟完全一致，计费功能验收通过。** 核心指标：透传 tokens 100% 一致、各模型/分辨率/V2V 单价与官方刊例价逐项吻合、vip 折扣正确、失败任务无异常扣费。
